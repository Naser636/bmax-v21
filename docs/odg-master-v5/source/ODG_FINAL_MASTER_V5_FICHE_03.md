205. Fundamental Principle
ODG does not automatically copy or integrate an external solution. It extracts the relevant principle, verifies compatibility and provenance, then constructs or selects the smallest adaptation capable of improving a specific ODG capability.
"Do not copy" means: - no uncontrolled automatic integration; - no blind dependency acquisition; - no automatic promotion; - no assumption that an external implementation belongs inside ODG; - no automatic architectural imitation.
It does not prohibit lawful and authorized reuse.
ODG may use an approved external library, API, model, framework, partner capability or reference implementation when license, provenance, security, compatibility, cost, maintenance, reversibility and value have been evaluated.

206. Four-Way Separation
EXTERNAL IDEA ≠ EXTERNAL IMPLEMENTATION ≠ ODG ADAPTATION ≠ ODG NATIVE CAPABILITY
An external idea may be studied and summarized.
An external implementation may be reused only when legally permitted, technically compatible, explicitly authorized, provenance-known, scoped and removable.
An ODG adaptation must be scoped, versioned, tested, measurable and reversible.
An ODG native capability must earn stable status through repeated evidence and justified permanence.
Using something once does not make it native.

"Newer" is not proof of improvement.

217. Sandbox First
New external implementations enter a controlled environment first.
Possible controls: - bounded resources; - bounded execution time; - controlled data; - restricted network; - minimal permissions; - isolated filesystem; - disposable environment; - evidence capture.
Establish functionality, operating conditions, cost, regressions, reproducibility, provenance and licensing.
Unknown external code is not trusted merely because it is popular.

227. Native Promotion
An adaptation becomes a native capability only when: - the internal problem is real; - usefulness is demonstrated; - benefit is reproducible; - scope is known; - risks are acceptable; - provenance is preserved; - licensing is acceptable; - recovery is available; - maintenance is justified; - permanence has evidence.
The experimenter/generator cannot unilaterally promote its own creation.

229. Anti-Accumulation Law
Every new dependency, model, library, adapter, module, provider, dataset, runtime service or integration must answer:
WHAT SPECIFIC CAPABILITY DOES THIS IMPROVE?
WHAT EVIDENCE PROVES THE IMPROVEMENT?
WHAT DOES IT COST?
WHAT DOES IT REPLACE OR SIMPLIFY?
HOW IS IT REMOVED?
WHY SHOULD IT BE PERMANENT?
If the answer is weak:
DO NOT ADD IT.
Sometimes the correct learning outcome is:
UNDERSTAND → REJECT → RECORD WHY
Rejection is learning.
